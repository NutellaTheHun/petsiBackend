## Overview

The `dynamic-properties` module implements a generic, admin-configurable "custom fields" system. It has exactly one first-class concept split into two conceptual layers, even though only one of those layers physically lives in this directory:

- **`DynamicPropertyConfig`** (`entities/dynamic-property-config.entity.ts`) — the *schema*/definition row: which holder entity type the property applies to (`HolderEntityType.MenuItem` today — an enum with a single member, clearly designed to be extended), an optional `holderCategory` scoping the config to only menu items in a given `MenuItemCategory`, a `propertyName`, and a `valueType` (`ValueType.EntityReference` or `ValueType.Filepath`). A computed, non-persisted `fieldRenderType` (`'entity-select' | 'file-upload'`) is derived from `valueType` via `deriveFieldRenderType()` and recomputed on every load via the `@AfterLoad()` hook `computeFieldRenderType()` — it is never stored in the DB column set.
- **The *value* row lives outside this module**, in the consuming domain: `MenuItemDynamicPropertyValue` (`src/modules/menu-items/entities/menu-item-dynamic-property-value.entity.ts`). Each row is a `(menuItem, config)` pair (unique together) holding either a free-text `valueText` or a `valueEntity` (self-referencing `MenuItem`, used when `valueType === EntityReference`, e.g. "this pastry's vegan counterpart is menu item #42").

This module only owns the **config** side — its own `builders/`, `controllers/`, `services/`, `validators/`, `dto/` subdirectories are all named `dynamic-property-config.*`. There is no `dynamic-property-value` builder/service/controller in this directory; value persistence, change detection, and snapshotting are implemented inside the consuming module (`menu-items`), which imports `DynamicPropertyConfigService` to validate against configs.

A dynamic property "attaches" to a domain entity (currently only `MenuItem`) via a join entity + an `@AfterLoad()` projection, not via a JSONB blob: `MenuItem` has `@OneToMany(() => MenuItemDynamicPropertyValue, ... { eager: true }) dynamicPropertyValues`, and its own `@AfterLoad() computeDynamicProperties()` flattens those rows plus their eagerly-loaded `config` into a read-friendly `dynamicProperties: DynamicPropertyResponseItem[]` array (config id, property name, render type, value type, and the resolved `value` string — either `valueEntityId` or `valueText` depending on `valueType`).

Only `menu-items` actually consumes this module today: no other module (inventory, recipes, labels, etc.) references `DynamicPropertyConfig` or dynamic property values.

Key relationships:
- `DynamicPropertyConfig *—1 MenuItemCategory` (two independent nullable FKs, both `onDelete: 'SET NULL'`, both `eager: true`): `holderCategory` scopes which menu items can use the config; `valueEntityCategory` (only meaningful when `valueType === EntityReference`) restricts which category the *referenced* menu item must belong to.
- `DynamicPropertyConfig 1—* MenuItemDynamicPropertyValue`, `onDelete: 'CASCADE'` — deleting a config wipes all values that reference it.
- `MenuItem 1—* MenuItemDynamicPropertyValue`, `onDelete: 'CASCADE'` — deleting a menu item wipes its own dynamic property values.
- `MenuItemDynamicPropertyValue *—1 MenuItem` via `valueEntity`, `onDelete: 'SET NULL'` — if the *referenced* menu item is deleted, the value row survives with a null reference rather than being deleted.
- `@Unique(['holderEntityType', 'propertyName'])` on `DynamicPropertyConfig` and `@Unique(['menuItem', 'config'])` on `MenuItemDynamicPropertyValue` — one property name per holder type, one value per menu-item/config pair.
- `DynamicPropertiesModule` exports only `DynamicPropertyConfigService`; `menu-items` imports it directly (e.g. `MenuItemValidator`'s constructor) rather than importing `DynamicPropertiesModule` wholesale in production wiring.

## Enforced Patterns

- **Structural fields on a `DynamicPropertyConfig` become immutable once any value row exists.** `DynamicPropertyConfigValidator.validateIdentity` compares incoming vs. existing fields (`holderEntityType`, `holderCategoryId`, `valueType`, `valueEntityType`, `valueEntityCategoryId`) and, only if at least one changed, checks whether any `MenuItemDynamicPropertyValue` references the config. If so, every changed field gets an `IMMUTABLE_FIELD` error and the whole update is rejected. `propertyName` is deliberately excluded from this check — renaming a config is always safe because values reference the config by id, not name. Any new field added to `DynamicPropertyConfig` that changes the shape of existing values must be added to this changed-field list.
- **`propertyName` uniqueness is scoped per `holderEntityType`, not global**, both at the DB level (`@Unique(['holderEntityType', 'propertyName'])`) and in the validator, which raises `ALREADY_EXISTS` on `propertyName` only within the same holder type.
- **`valueEntityType` is conditionally required, in three places, and must stay consistent**: the DTO-level `@ValidateIf` check, the validator-level `MISSING_PROPERTY` check, and `deriveFieldRenderType`. Adding a new `ValueType` member requires updating all three together — nothing enforces they stay in sync structurally.
- **Config validation is cross-checked again, per-value, from the consuming module.** `MenuItemValidator.validateIdentity` does not trust that a `configId` submitted in a menu item's `dynamicProperties` array is valid for that menu item — it re-verifies the config's `holderEntityType`, its `holderCategory` against the item's effective category, and (for `EntityReference` values) that the referenced menu item exists and matches any `valueEntityCategory` constraint. A dynamic property value can fail validation purely because the menu item's own category changed, independent of the value itself.
- **Changing a menu item's category can orphan its existing dynamic property values, and this is actively guarded against.** `DynamicPropertyConfigService.hasStaleDynamicPropertyValues(menuItemId, newCategoryId)` flags any value whose config has a category-scoped `holderCategory` that doesn't match the new category. `MenuItemValidator` calls this whenever `categoryId` is being changed on an existing item and rejects the update if stale values would result — the category-scoped properties must be cleared first, the API will not do it for you.
- **`dynamicProperties` in create/update DTOs is a sparse "set or clear" list, not a full replacement of all properties.** `MenuItemService.persistDynamicPropertyValues` iterates only the entries present in the DTO: `value === null` on an update deletes the matching value row (on create it's a no-op); a non-null value upserts by `(menuItem, config)` and re-derives which column to write from the *current* `config.valueType`. Properties omitted from the array are left untouched — sending an empty/undefined array on update does not clear existing values.
- **`MenuItemChangeDetector.hasDynamicPropertyChanges`** matches this sparse-update semantics — it never flags a property as changed just because it's missing from the incoming array entirely, only entries actually present are compared. When there is a change, the entire incoming `dynamicProperties` array is passed through as the patch (whole-array replacement), not a per-entry diff.
- **Revision history/snapshot support for dynamic properties is versioned and reverting fully replaces value rows.** `MenuItemSnapshotV2` adds `dynamicProperties` on top of V1; `applyMenuItemSnapshotV2` deletes every existing value row for the menu item and recreates rows from the snapshot, bypassing `persistDynamicPropertyValues` and the validator entirely — a revert referencing a since-deleted `configId` would fail via the FK.
- **`fieldRenderType` must never be persisted or set directly** — it's derived purely from `valueType` in `@AfterLoad()` hooks, which don't fire on a freshly-constructed/saved entity in the same transaction. `DynamicPropertyConfigService.createEntity`/`updateEntity` manually reassign it after `manager.save` for this reason — omitting that reassignment would leave the field `undefined` on the create response.
