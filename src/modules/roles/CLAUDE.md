## Overview
Manages `Role` entities (e.g. `admin`, `manager`, `staff` — constants in `utils/constants.ts`) that gate access to endpoints across the app. `Role` is tenant-scoped: it carries a denormalized `tenantId` scalar column (not a relation, so `ServiceBase`-level tenant filtering never needs a join) and a `@Unique(['tenantId', 'name'])` composite constraint — role names are unique per-tenant, not globally. `Role` has a `ManyToMany` relation to `UserLocation` (`src/modules/locations`) rather than directly to `User` — a user holds a role per location assignment, not per account. Beyond the standard CRUD stack (entity, DTOs, builder, service, validator, controller, change detector), this module also owns `RoleGuard`, which is registered globally as an `APP_GUARD` in `AppModule` alongside the JWT `AuthGuard`. The `@Roles(...)` decorator (`src/common/decorators/PublicRole.ts`) attaches required-role metadata to a route/controller; `RoleGuard` reads that metadata via `Reflector` and checks it against `request.user.roles`, allowing the request through if no metadata is present.

## Enforced Patterns
- `RoleService extends TenantScopedServiceBase`, not `ServiceBase` directly — this is the deliberate exception in the base-class hierarchy that itself overrides `findOne`/`remove`/`applyScope` to layer tenant isolation around every CRUD path, so tenant isolation can't be forgotten per-domain. `createEntity` must still stamp `tenantId` explicitly via `this.getTenantId()` (reads from `RequestContextService`, never a client-supplied DTO field) since `TenantScopedServiceBase` doesn't do entity construction.
- Role name uniqueness is enforced per-tenant in `RoleValidator.validateIdentity` via `helper.enforceUnique(...)` scoped with `{ tenantId: this.requestContextService.get('tenantId') }` — not a DB unique constraint alone. `Role`'s `@Unique(['tenantId', 'name'])` is a second line of defense at the DB level, but it's the composite key (tenant + name), so the same role name is valid across different tenants; application-level validation is what produces the user-facing `ValidationErrorMap` error.
- `RoleChangeDetector` only diffs `name` — since `Role` has no other mutable scalar fields, this is the entire change surface; if a new mutable field is ever added to `Role`, it must be added here or updates to that field will silently no-op through `ServiceBase.update`'s short-circuit.
- `RoleController` is class-level `@Roles(ROLE_ADMIN)` — every route on this controller requires the `admin` role via `RoleGuard`, not just specific endpoints. There's no per-route role override in this controller; if a route here needs different access, use `@Roles(...)` on that method to override the class-level metadata (route-level metadata wins via `getAllAndOverride`).
- `RoleTestUtil.seedRoles(P, tenantId?)` creates prefixed throwaway roles (`role-a/b/c`) scoped to a tenant, per the repo-wide atomic-test pattern. If no `tenantId` is passed it lazily provisions (or reuses, by fixed subdomain, across the whole test run) one shared fixture `Tenant` so most fixtures don't need to plumb a tenant through — tests that actually exercise tenant-scoping behavior (cross-tenant isolation, uniqueness-per-tenant) seed and pass their own explicit `tenantId` instead.
