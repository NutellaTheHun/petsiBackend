## Overview

The one-way Square → Petsi integration. **Read the Square skill first** (`.claude/skills/square/SKILL.md`, and `sdk-reference.md` for exact `square@46` signatures): it holds the settled decisions, the link-table design, ingest rules and data-shape gotchas. This file only covers what the module's code itself enforces.

Current contents: the `SquareConnection` entity, the client factory, token encryption, the error boundary, the daily token refresh (`SquareTokenRefreshService`), the connection routes (`GET`/`DELETE /square/connection`, `POST /square/connection/authorize`, `PATCH /square/connection/default-category`), the OAuth callback (`GET /square/oauth/callback`), the `SquareLocationLink` table with its sync (`SquareLocationSyncService`, run from `SquarePostConnectService`) and the tenant-admin routes under `/square/location-links` (list, `PATCH :id/location`, `POST :id/create-location`, `PATCH :id/enabled`), and the catalog link tables (`SquareCategoryLink`, `SquareItemHint`, `SquareSizeAlias`, `SquareVariationLink`) with their sync (`SquareCatalogSyncService`), derivation (`SquareCatalogDerivationService`) and the read route `GET /square/catalog`, plus the mapping writes under `/square/catalog` (`PATCH items/:id/menu-item`, `PATCH size-aliases/:id`, `PATCH variations/:id`, `POST variations/:id/reset`, `PATCH categories/:id/enabled`, `PATCH modifiers/:id/mapping`, `PATCH modifiers/:id/enabled`, `POST review`, `GET size-alias-suggestions`) in `SquareCatalogMappingService`, and the `SquareModifierLink` table (synced by `SquareCatalogSyncService`, propagated by `SquareModifierPropagationService`), and order ingest: the `SquareOrderLink` and `SquareUnresolvedLine` tables, the pure `mapSquareOrder` (`utils/square-order-mapper.ts`) and `SquareOrderIngestService` (all three modifier modes; fixed containers are expanded from their definition). Order responses get their Square flags from `OrderSquareStatusService` in the orders module. Also the webhook endpoint (`POST /square/webhooks`, `SquareWebhookController` → `SquareWebhookService`, pure payload parser `utils/square-webhook-event.ts`, dedupe table `SquareWebhookReceipt`). Also the initial import / re-sync (`SquareLocationImportService`, pure window `utils/square-import-window.ts`, route `POST /square/location-links/:id/resync`). Also order issues (`SquareOrderIssue`, written only by ingest; staff routes under `/square/locations/:locationId/order-issues` in `SquareOrderIssueService`). Detach: `SquareOrderController` / `SquareOrderDetachService`. Cancellation and refunds: `SquareOrderIngestService.cancel` / `flagCancelledWhileDetached` / `flagNewReturns`, with the pure `isSquareOrderCancelled` and `squareRefundSummary` in `utils/square-order-mapper.ts`.

## Enforced Patterns

- **Client factory is the only seam towards Square.** `SquareClientFactory` (`client/square-client.factory.ts`) is the only code that constructs a `SquareClient`. `forConnection(connection)` refuses unless `status === 'connected'` (`needs_reauth` → `SquareReauthRequiredException`, otherwise `SquareNotConnectedException`), decrypts the access token and returns a `SquareTenantApi`. `forApp()` returns a tokenless `SquareAppApi` for OAuth calls. Environment is Sandbox unless `NODE_ENV === 'production'`; the API version is pinned to `SQUARE_API_VERSION` (`utils/square-config.ts`).
- **`SquareTenantApi` / `SquareAppApi` (`client/square-api.ts`) list the allowed calls.** Reads only (plus `obtainToken`/`revokeToken`). They return plain `Promise`s, which `SquareClient` satisfies structurally. When a slice needs another read method, add it to the interface **and** to `unstubbedTenantApi()` in the fake. Never add a write.
- **Testing: `getSquareTestingModule()` always overrides the factory with `FakeSquareClientFactory`** (or `opts.squareClientFactoryClass`). The fake only replaces client construction (`createTenantClient`/`createAppClient`), so the status check and decryption still run. Specs assign typed `Square.*` fixtures to `fake.tenantApi.<resource>.<method>` / `fake.appApi.oAuth.<method>`, call `fake.reset()` in `beforeEach`, and can read `fake.tenantAccessTokens` (decrypted tokens the factory was asked to use). Unstubbed methods reject with "not stubbed". A domain module that calls Square must add this same override to its own testing module.
- **Tokens are encrypted at rest by `SquareTokenCryptoService`** (AES-256-GCM, stored as `v1:<iv>:<tag>:<ciphertext>`), keyed by `SQUARE_TOKEN_ENCRYPTION_KEY` (base64 of 32 bytes). The key is read on first use, so the app boots without it; any encrypt/decrypt then fails. The testing module loads a random key per module. Errors never contain the key, token or ciphertext.
- **`SquareConnection` is never returned from an endpoint.** It has no `@ApiProperty` and holds the encrypted tokens; map it to `SquareConnectionStatusDto`. Tokens never go in a response, DTO, log or revision snapshot.
- **`SquareConnectionService` is not a `ServiceBase`.** The connection is written by the OAuth flow and read on the webhook path (no request context), so methods that can run outside a request take `tenantId` explicitly; only `*ForCurrentTenant` methods read it from `RequestContextService`.
- **Error boundary (`client/square-error-boundary.ts`).** Tenant calls go through `SquareConnectionService.callTenant(connection, (api) => api.x.y(...))`: it builds the client, converts errors via `callSquare`, and on a Square 401 marks the connection `needs_reauth` (row and in-memory entity) before rethrowing. Never call `clientFactory.forConnection(...)` directly from a domain service. App-level OAuth calls use `callSquare` / `toSquareAppException` directly. Square 401 → `SquareReauthRequiredException` (409 `SQUARE_REAUTH_REQUIRED`, deliberately not 401 so the frontend doesn't log the user out; catch this type to set `needs_reauth`); 404 → `SquareNotFoundException` (404 `SQUARE_NOT_FOUND`); timeouts and everything else → `SquareUpstreamException` (502, which the global filter turns into an opaque 500 and logs; its message carries only the status and Square error codes, never `detail` or `body`). Non-Square errors pass through. Nothing here logs. The client-visible codes are listed in `ERROR_RESPONSE_CODES`.
- **Access.** Every Square controller carries `@RequiresFeature(FEATURE_REGISTRY.SQUARE_INTEGRATION)`, except the webhook and OAuth callback. Tenant-admin-only routes use `@UseGuards(TenantAdminGuard)` (`isTenantAdmin === true`); `@Roles(ROLE_ADMIN)` is not enough, since it passes an admin of one location. Route guards run after the global ones, so a tenant without the flag gets the feature 403 first.
- **OAuth state (`SquareOAuthStateService`).** A JWT with audience `square-oauth-state`, signed with an HMAC of `SQUARE_APPLICATION_SECRET` (never `JWT_SECRET`, so it can't pass `AuthGuard`). Its nonce is a `SquareOAuthState` row, deleted on `consume`, so states are single-use. `issue(tenantId, userId, ttlSeconds)` takes a TTL so specs can mint an expired state. The callback takes the tenant only from the verified state.
- **The OAuth callback always redirects** to `SQUARE_SETTINGS_URL?square=<outcome>` (`SQUARE_OAUTH_OUTCOMES`). Only unexpected errors (Square upstream failures) are thrown, so the global filter logs them.
- **Post-connect syncs go in `SquarePostConnectService.run(connection)`**, called by the callback after the connection is saved. Never import orders from it.
- **Disconnect:** `disconnectForCurrentTenant()` revokes (by `merchantId`, with `Authorization: Client <secret>` in request options; a Square 401 counts as already revoked), then calls `markDisconnected(tenantId)`. The revocation webhook calls `markDisconnected` directly. Neither touches link tables.
- **Token refresh (`SquareTokenRefreshService`).** Daily cron (04:00) → `refreshExpiring(now?)`, which refreshes every `connected` connection expiring within `SQUARE_REFRESH_WINDOW_DAYS` (7) or with no expiry, one connection at a time, and returns tenant ids per outcome. 401 / 400 `invalid_grant` → `markNeedsReauth`; any other failure leaves it `connected` for the next run and logs a `PinoLogger` warning (tenant id + converted message only — the one place outside the global filter that logs Square errors, since a cron has no request). Token writes and `markNeedsReauth` are conditional on `status = 'connected'`, so a concurrent disconnect is never undone. Specs: leftover connections from other runs use a different encryption key and land in `failed`; assert only on your own rows.
- **Link-table services are not `ServiceBase`s.** Syncs run without a request context (OAuth callback, webhooks), so sync services take the tenant from the `SquareConnection`; tenant actions live in a separate `*ForCurrentTenant` service that 404s on another tenant's row. Syncs write only Square-side columns (`update` for existing rows, `insert … orIgnore` for new ones) and auto-match only on insert. Name matching uses `normalizeSquareName` (`utils/square-name.ts`).
- **Location links:** only a mapped link can be enabled (`MISSING_PROPERTY` on `locationId`); unmapping also disables. Enabling (false → true only) first calls `requireConnection` (409 `SQUARE_NOT_CONNECTED` / `SQUARE_REAUTH_REQUIRED`, link stays disabled), then `importLocation(link, userId)`; a failed import leaves the link enabled for re-sync. "Create Petsi location" goes through `LocationService.create` and then clears `LocationController`'s findAll cache through the `CACHE_MANAGER` that `LocationsModule` exports.
- **Import / re-sync (`SquareLocationImportService`).** `importQueries(now)`: two `orders.search` runs per location, both `PICKUP`/`DELIVERY` with cursor paging: every `OPEN` order, and `COMPLETED` orders closed within `SQUARE_IMPORT_COMPLETED_LOOKBACK_DAYS` (30; sorted by `CLOSED_AT`, which Square requires when filtering on it). Don't drop the bound: it stops an import paging through the merchant's whole history → keep `isDueTodayOrLater(order, link.timezone, now)` (local calendar day; UTC fallback; no due time = left out) → `ingest(..., { actorUserId })`. A `rejected` ingest outcome is counted as `rejected` and the import continues. Re-sync (`POST :id/resync`) needs an enabled link (`INCONSISTENT_STATE` on `enabled`) and is throttled by `SQUARE_RESYNC_THROTTLE`. Never call it from a cron or the OAuth callback.
- **Catalog sync (`SquareCatalogSyncService`)** always uses `catalog.search` with `includeDeletedObjects: true` (never `catalog.list`, which has no deleted objects and no `latestTime`). `fullSync` = `syncSince(connection, undefined)`; an incremental sync passes `catalogSyncedAt`. Both page by `cursor`, `apply` the batch (categories → items → aliases → variations; order matters), run `deriveForTenant`, then store `latestTime`. Items carry their variations inline; top-level `ITEM_VARIATION`s take item fields from the stored hint. A variation's `isArchived` is its item's; a deleted item flags all its variation links.
- **Derivation** is the pure `deriveVariationMapping` (`utils/square-catalog-derivation.ts`). `deriveForTenant` rewrites only non-manual links whose mapping changed (conditional on `mappingSource = 'derived'`) and returns `newlyMappedLinkIds`. Call it after any hint or alias change. Empty variation names get no alias, so their links stay unmapped.
- **Catalog mapping writes (`SquareCatalogMappingService`).** Every hint/alias change ends in `afterMappingChange` (`deriveForTenant`, then `SquareLineConversionService.convertForVariationLinks` with `newlyMappedLinkIds`: the pending-line conversion hook task 15 fills in). Any variation override (even `enabled` alone) sets `mappingSource = 'manual'` and `reviewedAt`; the merged mapping is checked by `SquareVariationLinkValidator` (a plain injectable building a `ValidationErrorMap`, since link tables aren't `EntityBase`s). Reset sets `derived`, re-derives, and takes `enabled` from the category link. Category toggles update only `derived` links.
- **Modifier links.** The sync applies categories → items → aliases → variations → modifiers, then `fillUnmappedFromSiblings`, then auto-matches new rows (one SINGLE menu item by name, with exactly one size, or nothing). `squareItemIds` (a sorted `text[]`) is shared by every modifier of a list: an item in the batch restates its lists (a deleted item keeps its last ones). Siblings = same normalized name and an overlapping `squareItemIds` (`areModifierSiblings`); never across items. Tenant mapping writes set `manual` + `reviewedAt` and call `propagateFrom`, which writes only `derived` siblings. A modifier's category `enabled` comes from all its items (`modifierEnabledFromCategories`). `modifier_is_item` on a variation needs a live modifier link whose `squareItemIds` contains the variation's item.
- **Catalog access:** `@Roles(ROLE_ADMIN, ROLE_MANAGER)` without `@LocationScope` (tenant-wide); not `TenantAdminGuard`.
- **Specs:** link tables have no tenant FK, so delete them by `tenantId` before deleting the tenant. Any spec that runs the OAuth callback must stub `fake.tenantApi.locations.list` and `fake.tenantApi.catalog.search`, and delete the catalog link tables by `tenantId`. Delete `SquareModifierLink` rows by `tenantId` too (before variation links). `CatalogBatch.modifierLists`/`modifiers` are optional, so specs calling `apply` without them are unaffected. Any spec that enables a location link (service or HTTP) must seed a `connected` connection and stub `fake.tenantApi.orders.search`. Spying on `RevisionHistoryService.appendRevision` returns the shared default mock, so call `mockClear()` first. Any spec that ingests a rejected order must delete `SquareOrderIssue` rows by `tenantId`.
- **Testing config:** `getSquareTestingModule()` loads `SQUARE_TEST_CONFIG` (application id, redirect URL, settings URL) plus a random application secret; specs assert against `SQUARE_TEST_CONFIG`.
- **Order ingest (`SquareOrderIngestService.ingest`)** is the one path for a full Square order: location link → version check (`squareVersion` is a bigint string; compare with `BigInt`) → pure `mapSquareOrder` → write. Writes run inside `requestContext.runWithContext({ tenantId, isTenantAdmin: true, userId: actorUserId, locations: undefined, roles: undefined }, …)`, because the order validators read `tenantId` from the context. The line map is rebuilt after each write by matching menu item and size (unique per order), excluding staff item ids. Skipped orders write no `SquareOrderLink`.
- **Modifier modes and boxes (`mapSquareOrder`).** Ingest passes modifier links and container definitions (`loadModifiers`/`loadContainers`) into the pure mapper. Container rules (total = `variableMaxAmount`, contents in the box's allowed list for that size, merged by menu item:size) are checked in the mapper, so a bad box becomes a `container_invalid` line instead of an `OrderService` rejection. Ignored and disabled modifiers never block a line; in `none` mode modifiers are not read at all. A variable container in `none` mode is `container_invalid`, never an empty box. One Square line can plan several items: `lineMap[uid]` holds all of them and create ids are `<uid>/<menuItemId>:<sizeId>`.
- **Order issues.** `ingest()` never throws `ValidationException`: a mapper or `OrderService` rejection, or an enabled link with no Petsi location, goes through `reject()` → upserts the order's `SquareOrderIssue` (`validation_failed` with `detail.validationErrors` = the client tree, or `location_unmapped`) and returns `{ outcome: 'rejected' }`. Nothing else is written; the order link keeps its old version so the next update retries. Scope skips (`squareOrderSkipReason`) come first, so an out-of-scope order never gets an issue. A successful write resolves an open `SQUARE_RETRYABLE_ISSUE_REASONS` issue in the same transaction as the link. A dismissed issue stays dismissed. The issue's `locationId` (the existing order's, else the link's; null if neither exists) is what the location-scoped routes filter on.
- **Issue routes** use `@Roles(ROLE_ADMIN, ROLE_MANAGER)` + `@LocationScope('params', 'locationId')` with the location in the path, and the service 404s for an issue at another location. Retry re-fetches the order with `orders.get` and runs ingest with the caller as actor.
- **Order responses read the Square tables through `OrderSquareStatusService` (orders module)**, not through `SquareModule`, which imports `OrdersModule`.
- **Webhook (`SquareWebhookService.handle`).** Verify over `req.rawBody` (403 on mismatch) → parse snake_case → connection by `merchant_id` → `oauth.authorization.revoked` always `markDisconnected` (any status, no flag check) → drop (200) unless `connected` + `SQUARE_INTEGRATION` → claim `SquareWebhookReceipt` by `eventId` (`insert … orIgnore`; no row inserted = duplicate) → process. Unexpected errors delete the receipt and rethrow (500, Square redelivers); A `rejected` ingest outcome and Square reauth/not-connected/not-found are acknowledged. Order events skip the fetch when the event's version ≤ the link's `squareVersion`. The route is excluded from `TenantResolutionMiddleware` in `AppModule` (`SQUARE_WEBHOOK_PATH`).
- **Revision actor.** Ingest without `actorUserId` sets `revisionActorType: 'square_webhook'` in its `runWithContext`; `getRevisionActor` checks that key before `userId`. Import/re-sync/resolution must pass `actorUserId`.
- **Ownership and Detach.** Ingest and line conversion set `squareSystemWriter: true` in their `runWithContext`; without it, `OrderValidator` rejects staff changes to a linked order's Square-owned fields (`SQUARE_OWNED_ORDER_FIELDS` in `orders/utils/square-ownership.ts`) and Square-derived items (ids in `lineMap`) with `IMMUTABLE_FIELD`. Values equal to the current ones pass, so a full DTO echoing the order is fine. `note` and `fulfillmentContactName` stay Petsi-owned (ingest never writes them). The line DELETE routes and `revertToRevision` go through `OrderSquareStatusService.assertNotSquareOwned`. Any new system writer of Square-owned data must set the flag. Detach (`POST /square/locations/:locationId/orders/:orderId/detach`, `SquareOrderDetachService`) sets the link `detached`, clears `lineMap`, dismisses pending lines; 404 unless the order is at that location and has a link; idempotent.
- **Cancellation and refunds (ingest).** Order: detached → `isSquareOrderCancelled` ? `cancelled_while_detached` issue (once; none if the order is already `CANCELLED` or gone) : skip → stale check → linked + cancelled → `cancel()`: status-only `OrderService.update` as system writer, link version bumped, pending lines dismissed, open retryable issue resolved; outcome `cancelled`. A never-imported cancelled order is skipped (`cancelled`) and its open retryable issue resolved. Returns: after a successful write, a return uid not in the issue's `detail.refund.returnUids` (re)opens a `refund_received` issue; lines are never changed. `findImportedFulfillment` prefers a fulfillment that isn't CANCELED/FAILED. Fulfillment progress states are never read.
- **Webhook specs** sign with `createHmac('sha256', SQUARE_WEBHOOK_SIGNATURE_KEY).update(SQUARE_TEST_CONFIG.webhookNotificationUrl + body).digest('base64')` and send the body as a string with `content-type: application/json`. Delete `SquareWebhookReceipt` rows by `tenantId` in per-test cleanup.

## Gotchas

- 2026-10-28 — `forConnection()` only reads `status` and `accessToken`, so the callback calls it (through `callTenant`, which skips the DB update for an unsaved row) on an *unsaved* entity to fetch the merchant profile before saving — keep it free of DB lookups, or the callback's merchant fetch breaks.
- 2026-10-29 — `npx prettier --write src/modules/square` also rewrites this CLAUDE.md (`*x*` → `_x_`) — run prettier on the code subdirectories only.
- 2026-10-29 — `TenantResolutionMiddleware` (AppModule, all routes) 404s any request whose host subdomain isn't a tenant, and `createHttpTestApp` doesn't apply it, so HTTP specs can't catch it — app-level Square URLs (`SQUARE_WEBHOOK_PATH`, `SQUARE_OAUTH_CALLBACK_PATH`) are excluded in `AppModule.configure`; a new app-level route must be added there.
- 2026-10-29 — Assumed whole-order rejections came only from `OrderService`; `mapSquareOrder` itself throws `ValidationException` for missing recipient/due time/bad quantities — ingest catches both (around the mapper and around the write) and records an issue.
