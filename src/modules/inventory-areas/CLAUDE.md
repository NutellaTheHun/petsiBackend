## Overview

This module owns the "physical inventory counting" workflow: `InventoryArea` (a named storage location, e.g. "Walk-in" or "Dry Storage"), `InventoryAreaCount` (one counting event/session tied to an area), and `InventoryAreaItem` (a single counted line — an `InventoryItem` + `InventoryItemSize` + `amount` — nested under a count). The nesting is two levels deep and modeled the same way `orders` models `Order → OrderMenuItem`: `InventoryAreaCount.countedInventoryItems` is a `@OneToMany` to `InventoryAreaItem` with `cascade: true`, and each `InventoryAreaItem` points back via `parentInventoryCount` (`@ManyToOne`, `onDelete: 'CASCADE'`, `orphanedRowAction: 'delete'`). `InventoryArea` itself is flat/non-hierarchical — no parent-area or sub-area concept, just a unique `name` and a `@OneToMany` back-reference to its `inventoryCounts`.

Both `InventoryAreaItem.countedInventoryItem` and `InventoryAreaItem.countedItemSize` are `@ManyToOne` references into the `inventory-items` module. The module wiring (`inventory-areas.module.ts`) imports `InventoryItemsModule` and also registers `InventoryItem`/`InventoryItemSize` directly in its own `TypeOrmModule.forFeature([...])` so its builders/validators/composer can query those repos. The dependency is one-directional at the module-import level (`inventory-areas` imports `inventory-items`, not vice versa), but `inventory-items/builders/inventory-item-size.builder.ts` accepts either an `InventoryItem` or `InventoryAreaItem` as its "parent" — sizes can be created on the fly as a side effect of recording an inventory count, not just when defining an `InventoryItem`.

Key relationships:
- `InventoryArea 1—* InventoryAreaCount 1—* InventoryAreaItem` (two levels of nested composition, cascaded from their parent, mirroring the `orders` module's `Order → OrderMenuItem` pattern).
- `InventoryAreaItem *—1 InventoryItem` and `InventoryAreaItem *—1 InventoryItemSize`, both from `inventory-items` (cross-module dependency; `InventoryAreasModule` imports `InventoryItemsModule`).
- `InventoryAreaCount *—1 InventoryArea`, both `onDelete: 'CASCADE'` with `orphanedRowAction: 'delete'` — deleting an `InventoryArea` deletes every `InventoryAreaCount` (and transitively every `InventoryAreaItem`) ever recorded for it; there is no soft-delete or archival here.
- `InventoryAreaItem.countedInventoryItem`/`countedItemSize` are also `onDelete: 'CASCADE'` — deleting an `InventoryItem` or `InventoryItemSize` cascades to delete every historical `InventoryAreaItem` row that referenced it, silently erasing count history for that item/size.
- `InventoryArea.name` is `@Column({ unique: true })`, enforced in code via `InventoryAreaValidator.validateIdentity` calling `enforceUnique`, not just the DB constraint.

## Enforced Patterns

- **`InventoryAreaItemValidator.validateIdentity` enforces "exactly one of `countedItemSize` (nested create) or `countedItemSizeId` (existing id), never both, never neither"** via `enforceOnlyOne`, which emits `ONLY_ONE` on either violation — the same helper documented in `src/common/validation/CLAUDE.md`. `InventoryAreaItemComposer` also defensively throws a raw `Error` if both are set on update or neither is set on create — the invariant is checked twice, once by the validator and once defensively inside the composer.
- **`InventoryAreaItemController.create`/`update` are dead endpoints that always throw `Error('Endpoint not available')`** — only `findAll`/`findOne`/`remove` are wired live. The only supported way to create or update an `InventoryAreaItem` is as a nested DTO inside `CreateInventoryAreaCountDto.countedInventoryItems`/`UpdateInventoryAreaCountDto.countedInventoryItems`. A newcomer wiring a direct item-update flow through this controller will get a runtime error, not a 404.
- **Updating a count's `countedInventoryItems` array is authoritative/whole-array-replacement, not a diff you send incrementally.** `InventoryAreaCountService.updateEntity` computes `idsToRemove` as every existing item id not present in the incoming DTO array and hard-deletes those rows before composing the rest. Sending `countedInventoryItems: []` on an update deletes every counted item under that count. This differs from `OrderMenuItem`'s pattern in `orders` — here removal is done by the service directly with a manual diff against ids, not via composer/orphan-row cascade alone.
- **Nested items are identified by `createId` (string) for new rows or `id` (number) for existing rows, resolved through `ComposerBase.composeManyNestedEntity`.** `UpdateInventoryAreaCountDto.countedInventoryItems` uses a `@Transform` that manually `plainToInstance`s each array element into the create or update variant based on whether `createId` is present — get this transform wrong (e.g. add a new nested DTO shape) and class-validator will validate against the wrong class.
- **`InventoryAreaItemValidator.validateIdentity` also enforces `amount` must be positive** (`enforcePositive`), that `countedInventoryItemId` must reference an existing `InventoryItem` (`enforceExists`), and — when both a size id and item id are present — that the size id is actually one of that item's valid sizes via `enforceValidSize`. Passing a `countedItemSizeId` that belongs to a *different* `InventoryItem` than `countedInventoryItemId` passes `enforceExists` but fails `enforceValidSize`.
- **`InventoryAreaCountValidator` and `InventoryAreaItemValidator` are mutually wired via `forwardRef`** because count validation recurses into each nested item's identity. Adding a new cross-reference between these two without `forwardRef` will produce a circular-DI error at bootstrap.
- **Change detection returns whole-array patches for `countedInventoryItems`, same shape as `orders` — but narrower.** `InventoryAreaCountChangeDetector.detectCountedItems` pushes through any new (`createId`-tagged) DTO untouched, and for existing items delegates to `InventoryAreaItemChangeDetector.detect`, only including the item in the patch if that nested detector reports `hasChanges` — only the changed nested items are forwarded, not the full array (unlike `orders`, where any change forces the entire nested array through).
- **`InventoryAreaItemChangeDetector.detect` does not diff the nested `countedItemSize` sub-object** — that comparison is commented out in the entity-transformer, so a change expressed only as a new nested `countedItemSize` DTO (rather than swapping to a different existing `countedItemSizeId`) will not be detected as a change by this comparison and relies on the composer/validator paths instead.
- **`InventoryAreaCountService.getUpdateDiffRelations()` must include every nested relation the detector needs** (`['inventoryArea', 'countedInventoryItems', 'countedInventoryItems.countedInventoryItem', 'countedInventoryItems.countedItemSize']`) — omitting one means the pre-update `findOne` won't have it loaded, and the change detector will compare against `undefined`, treating every nested item as "new" and causing false-positive updates.
- **`InventoryAreaBuilder`/`InventoryAreaCountBuilder`/`InventoryAreaItemBuilder` are test/seed-time construction helpers, not part of the request-handling path** — production create/update flows go through the composer, while the builders are consumed only by test-fixture utilities. Don't assume builder methods run on the live create/update HTTP path.
