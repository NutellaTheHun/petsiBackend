## Overview

`src/modules/auth` implements username/password login and JWT issuance for the whole application. It is a small module: `AuthController` exposes a single `POST /auth/login` endpoint, `AuthService` validates credentials and mints the token, `AuthGuard` is the global gatekeeper wired in `AppModule`, and `utils/hash.ts` wraps bcrypt for password hashing.

**Login flow** (`AuthController.signIn` → `AuthService.signIn`):
1. `AuthController.signIn` is decorated `@Post('login')` and `@Public()` (from `src/common/decorators/PublicLogin.ts`) so the global `AuthGuard` lets the request through without a token. It reads `tenantId` off `req['tenant']?.id`, set by `TenantResolutionMiddleware` before this handler runs (before auth, for every route, including this `@Public()` one) — never from the request body.
2. `AuthService.signIn(username, rawPass, tenantId)` loads the `User` via `userRepo.findOne({ where: { tenantId, name: username } })` — tenant-scoped lookup, so the same username can exist under different tenants and login only succeeds against the tenant resolved from the subdomain.
3. The raw password is compared against the stored bcrypt hash with `isPassHashMatch` (`utils/hash.ts`). Any failure (unknown user, wrong tenant, or bad password) throws `UnauthorizedException('Invalid username or password')` — the message is intentionally identical in every case so the endpoint doesn't leak whether a username or tenant exists.
4. On success it loads the user's `UserLocation` assignments (`userLocationRepo.find({ where: { user: { id: user.id } }, relations: ['roles'] })`) and builds a per-location `locations: { locationId, roles: string[] }[]` claim — a user's roles are attached per location assignment, not globally, so the same user can hold `manager` at one location and `staff` at another.
5. That same loaded `Role[]` data (which carries `id`, unlike the flattened role-name list) also feeds the feature-flags effective-features resolver: `AuthService` builds `roleGrantsByRoleId`/`userRoleIdsByLocation` from it, fetches `TenantFeatureService.findEnabledFeatures(tenantId)`, and calls `computeEffectiveFeatures` (`src/modules/feature-flags/utils/effective-features.resolver.ts`) with `user.isTenantAdmin` to get the signing-in user's effective `Feature[]` list. See `src/modules/feature-flags/CLAUDE.md` for the resolver's rules.
6. The JWT payload is `{ sub: user.id, username: user.name, tenantId: user.tenantId, isTenantAdmin: user.isTenantAdmin, locations, features }`, signed with `this.jwtService.signAsync(payload, { expiresIn: '1hr' })`.
7. The response (`AuthResponseDto`) returns `{ access_token, roles, features }`, where `roles` is `[...new Set(locations.flatMap(l => l.roles))]` and `features` is the same array baked into the JWT — both flattened/rendering-only fields. The actual authorization decision is always made from the verified JWT's `locations`/`isTenantAdmin`/`features`, never from this response body.

**Token verification / guard**: `AuthGuard` is registered globally via `APP_GUARD` in `src/app.module.ts`. On every request it:
- Checks `IS_PUBLIC_KEY` metadata via `reflector.getAllAndOverride`; if true, returns `true` immediately, skipping verification entirely.
- Otherwise extracts the bearer token from the `Authorization` header, and if missing throws `UnauthorizedException`.
- Verifies the token with `jwtService.verifyAsync(token, { secret: this.authService.getJwtSecret() })` (secret pulled from `JWT_SECRET` env var). Any verification failure (expired, bad signature, malformed) is caught and rethrown as a bare `UnauthorizedException` (401), never a more specific error.
- On success it stores the decoded payload on the request as `request['user'] = payload` — the only place `request.user` gets populated. This is also what `RoleGuard` reads directly (not `RequestContextService`) to make its role/location decision.
- It also pushes `payload.sub` (as `userId`), `payload.tenantId`, `payload.isTenantAdmin`, and `payload.locations` into the async request-context namespace (`getRequestNamespace()` from `src/modules/request-context/RequestContextService.ts`) when a context is active — each pushed individually and defensively type-checked, so a malformed/partial payload only skips the bad key rather than throwing.

**There are no refresh tokens.** `AuthModule`'s `JwtModule.registerAsync` sets a module-level default `signOptions: { expiresIn: '60s' }`, but `AuthService.signIn`'s explicit `signAsync(payload, { expiresIn: '1hr' })` call overrides that default per-call, so real access tokens are valid for 1 hour. There is no refresh-token endpoint, no token blacklist/revocation list, and no session storage.

**Password hashing**: `utils/hash.ts` uses `bcrypt` with `saltOrRounds = 10`. `hashPassword` is used by consumers (e.g. `UserService`) when creating/updating users — this module only verifies, via `isPassHashMatch`.

Key relationships:
- `src/modules/users` — `AuthModule` imports `UserModule` and injects the TypeORM `User` repository directly (`TypeOrmModule.forFeature([User])` in `auth.module.ts`) rather than going through `UserService`; `User` gains a required `tenantId` FK and an `isTenantAdmin: boolean` flag, both of which flow straight into the JWT payload.
- `src/modules/locations` — `AuthModule` also injects the `UserLocation` repository directly. `UserLocation` is the join entity carrying a user's roles per location assignment (replacing the old direct `User`↔`Role` many-to-many); `AuthService.signIn` loads a user's assignments (with their `roles` relation) and shapes them into the JWT's `locations: { locationId, roles: string[] }[]`.
- `src/modules/roles` — `Role` entity supplies the role `name` strings (`ROLE_ADMIN`/`ROLE_MANAGER`/`ROLE_STAFF` in `src/modules/roles/utils/constants.ts`) that end up nested under each location claim and are later checked by `RoleGuard` (`src/modules/roles/guards/role.guard.ts`).
- `src/modules/feature-flags` — `AuthModule` imports `FeatureFlagsModule` to get `TenantFeatureService` (constructor-injected normally, since it takes `tenantId` as an explicit argument rather than pulling it from context) and a directly-injected `Repository<RoleFeature>` (`@InjectRepository(RoleFeature)` in `AuthService`, exposed via `FeatureFlagsModule`'s `exports: [..., TypeOrmModule]`). `AuthService.signIn` uses both, plus `computeEffectiveFeatures`, to resolve the JWT's `features` claim — see the Gotchas entry below for why `RoleFeatureService` itself can't be used here.
- `src/common/middleware/TenantResolutionMiddleware` resolves `req['tenant']` from the subdomain before `AuthGuard` runs (middleware always executes before `APP_GUARD`-registered guards); `AuthController.signIn` reads `req['tenant']?.id` to scope the login lookup.
- `@PublicLogin()`/`@Public()` (`src/common/decorators/PublicLogin.ts`) is `SetMetadata(IS_PUBLIC_KEY, true)`, `IS_PUBLIC_KEY = 'isPublic'`; consumed exclusively by `AuthGuard`. It has no effect on `RoleGuard`.
- `@Roles(...roles)` (`src/common/decorators/PublicRole.ts`) is `SetMetadata(ROLES_KEY, roles)`, `ROLES_KEY = 'roles'`; consumed exclusively by `RoleGuard`, a separate module, not by anything in `auth/`.
- `src/app.module.ts` registers three global guards via repeated `APP_GUARD` provider entries, in this exact order: `AuthGuard`, then `RoleGuard`, then `ThrottlerGuard`. NestJS runs multiple `APP_GUARD` providers in registration order, so `AuthGuard` always populates `request['user']` before `RoleGuard` reads it.

## Enforced Patterns

- **Password hashing is bcrypt, cost factor 10 — never store or compare plaintext.** Any new code that creates/updates a user's password must call `hashPassword` from `utils/hash.ts` before persisting, and any comparison must go through `isPassHashMatch`; this module deliberately does not export a "verify plaintext == plaintext" path.
- **Guards are global-only; you do not add `AuthGuard`/`RoleGuard` per-controller.** Because both are bound as `APP_GUARD` in `src/app.module.ts`, every controller in the app is protected by default. The only levers a controller author has are the metadata decorators: `@Public()` to skip **JWT verification only**, `@Roles(ROLE_X, ...)` to require the JWT payload's `locations[].roles` contain at least one listed role name (at any location, or `isTenantAdmin`), and `@LocationScope(source, key)` (`src/common/decorators/LocationScope.ts`) to narrow that check to the role being held specifically at the `locationId` extracted from `params`/`query`/`body` — see `src/modules/roles/CLAUDE.md` for the location-aware check itself. If a route/class has no `@Roles(...)` at all, `RoleGuard.canActivate` returns `true` unconditionally — omitting `@Roles` means "any authenticated user," not "no access."
- **`@Public()` and `@Roles()` must never both apply to the same route.** `RoleGuard.canActivate` destructures `user` off the request and returns `false` immediately if it's missing. If `AuthGuard` skipped verification because the route is `@Public()`, `request['user']` is never set, so a route that's also `@Roles(...)`-guarded (whether directly or via class-level metadata) would be unconditionally denied rather than cleanly public. Because `Reflector.getAllAndOverride` walks handler-then-class, a `@Public()` method inside a controller carrying a class-level `@Roles(...)` (as `UserController` does with `@Roles(ROLE_ADMIN)`) would break unless that method also has no role requirement in effect. `AuthController.signIn` is safe today only because its controller has no class-level `@Roles(...)`.
- **Guard ordering is load-bearing.** `RoleGuard` depends on `AuthGuard` having already run and attached `request['user'] = payload`; this only works because `AuthGuard` is registered before `RoleGuard` in the `providers` array of `src/app.module.ts`. Reordering those `APP_GUARD` entries would make role checks read `undefined` on every non-public request.
- **Invalid/expired/malformed tokens all collapse to a bare 401.** `AuthGuard.canActivate` wraps `jwtService.verifyAsync` in a try/catch and rethrows every failure mode as a generic `UnauthorizedException()`. Do not rely on distinguishing "expired" vs "invalid" from the HTTP response — the client only ever sees 401 with no body detail.
- **There is no refresh-token flow or server-side revocation.** Tokens are valid for the full 1-hour lifetime set by the explicit `expiresIn: '1hr'` argument to `signAsync` in `AuthService.signIn` (this overrides the module-level `JwtModule.registerAsync` default of `60s` — don't assume that `60s` value is the real token lifetime). Changing a user's roles, location assignments, `isTenantAdmin` flag, or password, or deleting the user, does not invalidate already-issued tokens — those changes only take effect on the user's next login.
- **Role names must match exactly** between what's stored on `Role.name` and what's passed to `@Roles(...)` — comparison in `RoleGuard` is a plain string `.includes()` against each location claim's `roles` array, so `@Roles('Admin')` would not match a token containing `roles: ['admin']`. Use the shared constants in `src/modules/roles/utils/constants.ts` rather than hardcoding role strings in new controllers.

## Gotchas

2026-09-21 — `RoleFeatureService` (a `TenantScopedServiceBase` subclass) can't be used inside `AuthService.signIn` — its `getTenantId()` reads `tenantId` off `RequestContextService`'s async-local-storage context, which `AuthGuard` only populates *after* JWT verification succeeds; the `@Public()` login route never populates it, so any call would throw `NotFoundException`. `AuthService` instead injects `Repository<RoleFeature>` directly, mirroring how it already injects `User`/`UserLocation` repos directly rather than going through their services. Any future login-time lookup against a tenant-scoped entity needs either a direct repository injection (like this) or a plain service that takes `tenantId` as an explicit argument (like `TenantFeatureService`) — never a `TenantScopedServiceBase` subclass.
