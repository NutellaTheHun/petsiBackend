## Overview

This directory is the app's single translation layer between low-level failures (TypeORM/Postgres errors, validation errors, ad-hoc `HttpException`s) and the JSON error envelope every HTTP client sees. It has two halves: a set of typed exception classes/handlers that domain code (mostly `ServiceBase` and `BuilderBase`) throws or produces, and one `@Catch()` filter that turns whatever gets thrown into a uniform response body.

- `app-http-exception.ts` — `AppHttpException extends HttpException`. Constructor takes `(message, status, code?, details?)` and packs them into the Nest response body as `{ message, code, details }`. This is the one exception type meant to be thrown directly by application code when it needs to pick its own HTTP status/code (e.g. `BuilderBase.setPropById`/`setPropsByIds`/`setPropByName` in `src/common/base/builder.base.ts` throw `AppHttpException(..., HttpStatus.BAD_REQUEST, REFERENCE_NOT_FOUND, { id })` when a foreign-key id passed into a create/update DTO doesn't resolve to a real row).
- `error_constants.ts` — string constants (`ENTITY_NOT_FOUND`, `REFERENCE_NOT_FOUND`, `DTO_VALIDATION_FAIL`, `SOMETHING_WENT_WRONG`, `EXIST`, `DUPLICATE`, `INVALID`, `MISSING`) meant to populate `AppHttpException.code`. In practice only two are consumed: `ENTITY_NOT_FOUND` by `TenantResolutionMiddleware` (`src/common/middleware/TenantResolutionMiddleware.ts`) and `REFERENCE_NOT_FOUND` by `BuilderBase` (`src/common/base/builder.base.ts`); the rest are declared but not yet wired to a call site. `DTO_VALIDATION_FAIL` is superseded by the literal `INVALID_REQUEST` code the filter returns for `DtoValidationException`, so it can be removed.
- `database-error.ts` — `DatabaseError` (a plain `Error` subclass, not an `HttpException`) plus `DatabaseErrorCode` enum (`CONSTRAINT`, `NOT_FOUND`, `CONNECTION`, `UNKNOWN`). Its static `DatabaseError.fromTypeOrmError(error)` is the single place that inspects a raw error and classifies it (see Enforced Patterns). It always returns a `DatabaseException`, wrapping the classified `DatabaseError` inside.
- `database-exception.ts` — `DatabaseException extends Error`, carries the classified `DatabaseError` on `.error` and a generic `message` (`'Database error occured'` by default). This is what actually gets thrown up to controllers/the filter.
- `dto-validation-exception.ts` — `DtoValidationException extends Error`, thrown by the global `ValidationPipe`'s `exceptionFactory`. It holds the raw class-validator `errors`, which contain submitted values, so never serialize or log them. It also holds `dtoName`. `fieldPaths()`/`failedConstraints()` are the only safe views.
- `global-http-exception-filter.ts` — `GlobalHttpExceptionFilter` (`@Catch()` + `@Injectable()`, catches everything). Its constructor takes an `ExceptionFilterLogger` (a `Pick` of nestjs-pino's `PinoLogger`) injected via `@Inject(PinoLogger)` and an `ExceptionFilterRequestContext` (`Pick<RequestContextService, 'get'>`, read for `userId`/`tenantId`). It's the only place in the app that decides final `statusCode`/`message`/`code`/`details`/`requestId` for the HTTP response, and the only place that logs errors (see Enforced Patterns for the classification table).
- `error-response.dto.ts` — Swagger-only schemas for the error envelope (`ErrorResponseDto`, its `details` shapes, the validation error tree) plus `ERROR_RESPONSE_CODES` and `VALIDATION_ERROR_CODES` (derived from `VALIDATION_ERROR_CODE_LOGGED`). Registered as `extraModels` in `main.ts` so the generated frontend types include them. Keep `ERROR_RESPONSE_CODES` in step with the codes `classify()` returns.
- `exceptions.module.ts` — `ExceptionsModule`, imports `RequestContextModule` and provides/exports `GlobalHttpExceptionFilter` so DI can construct it. Imported by `AppModule`; domain testing modules don't import it.

Key relationships:
- **Shared app setup.** `setupApp(app, opts?)` in `src/app.setup.ts` is the single place that registers the request-id middleware, the global `ValidationPipe` and the global filter. `src/main.ts` calls it right after `NestFactory.create` (before Swagger), and the HTTP test harness calls it too. Never add pipe/filter/request-pipeline setup directly in `bootstrap()` — put it in `setupApp` so tests exercise it. By default `setupApp` registers `app.get(GlobalHttpExceptionFilter)` (the DI instance); `opts.exceptionFilter` overrides it.
- **Request-id contract** (`src/common/middleware/request-id.ts`). `resolveRequestId(req)` is idempotent: it reuses `req.requestId` if already set, else the client's `x-request-id` header, else a fresh UUID, and stores it on `req.requestId`. `setupApp` registers `requestIdHeaderMiddleware` via `app.use` (before `app.init()`, so ahead of all module middleware, pino-http included), which resolves the id and sets the `X-Request-Id` response header on **every** response. `RequestIdMiddleware` (CLS context), pino-http's `genReqId`/`customProps` (`pinoHttpRequestIdOptions`, spread into `AppModule`'s `LoggerModule.forRoot`) and the filter's `requestId` envelope field all call `resolveRequestId`, so the access line, request context, header and error body share one id regardless of middleware order. Verified by `src/common/middleware/request-id.spec.ts`.
- **HTTP test harness** (`src/test/http-test-app.ts`). `createHttpTestApp(compiledTestingModule, { beforeInit? })` creates the app, calls `setupApp` with a filter constructed around a `RecordingLogger` (captures `{ level, payload, msg }` per call in `logger.logs`) and the testing module's `RequestContextService` (so `TestRequestContextService.setContext({ userId, tenantId })` shows up in log entries), runs `beforeInit` (e.g. to add global guards), then `app.init()`. Use it for any test that asserts on status/body/headers/logs over supertest. Example: `global-http-exception-filter.http.spec.ts`.
- `src/common/base/service.base.ts` (`ServiceBase`) is the sole real caller of `DatabaseError.fromTypeOrmError`, wrapping every `create`, `update`, `findAll`, `findOne`, `remove`, and `getQueryBuilder` DB call in `try { ... } catch (err) { throw DatabaseError.fromTypeOrmError(err); }`. The conversion does not log — the filter does. Since virtually every domain module has a service extending `ServiceBase`, this path is exercised on essentially every write and most reads across the app, even though no domain module imports `DatabaseError`/`DatabaseException` directly.
- `src/common/base/builder.base.ts` (`BuilderBase`) imports `AppHttpException`/`REFERENCE_NOT_FOUND` directly and throws them when a queued `setPropById`/`setPropsByIds`/`setPropByName` step can't resolve a related entity. These surface as 400s with `code: 'REFERENCE_NOT_FOUND'`, logged at `warn` with `source: 'business'` and `id`/`ids` (never `name`), distinct from the DB-error path. Builders are currently only used by test seeding utilities (`*-testing.util.ts`), not by production services; if one ever runs inside `createEntity`, the transaction catch turns its exception into a 500.
- `src/common/base/composer.base.ts` (`ComposerBase`) calls `manager.findOneOrFail(...)` for the update branch of `composeNestedEntity`/`composeManyNestedEntity`. TypeORM's `EntityNotFoundError` thrown there propagates out through the enclosing `ServiceBase.create`/`update` transaction's `try/catch`, so it too ends up going through `DatabaseError.fromTypeOrmError` (matched by the `error.name === 'EntityNotFoundError'` branch) rather than as a clean 404.
- `src/common/validation/validation-exception.ts` is a sibling pattern (a plain-`Error` exception carrying the payload), and `GlobalHttpExceptionFilter` special-cases `ValidationException` the same way it special-cases `DatabaseException`.
- `ServiceBase.update` calls `findOne` **outside** any `DatabaseError.fromTypeOrmError` try block, so a missing (or other-tenant/unauthorized-location) id on `PUT /:id` surfaces as a 404 with no filter log. `findOne` wraps its own query errors. Covered by `order.controller.spec.ts` ("updateOrderResponse throws NotFoundException for a missing order") and the HTTP filter spec.

## Enforced Patterns

- **DB error classification happens in exactly one place and only recognizes two Postgres codes.** `DatabaseError.fromTypeOrmError` (`database-error.ts`) only special-cases `error instanceof QueryFailedError` with `pgError.code === '23505'` (unique violation → `DatabaseErrorCode.CONSTRAINT`) and `pgError.code === '23503'` (foreign key violation → `DatabaseErrorCode.CONSTRAINT`). Every other `QueryFailedError` falls into `DatabaseErrorCode.UNKNOWN`. Separately, `error.name === 'EntityNotFoundError'` maps to `DatabaseErrorCode.NOT_FOUND`. Anything else (plain `Error`s, Nest `HttpException`s like `NotFoundException`/`BadRequestException` thrown inside a `ServiceBase` try block, connection errors, etc.) falls through to `DatabaseErrorCode.UNKNOWN` too — there is no explicit `DatabaseErrorCode.CONNECTION` producer despite the enum value existing. A new Postgres error code that needs distinct handling (e.g. `23502` not-null, `23514` check) must be added as a new branch in `fromTypeOrmError`.
- **`DatabaseErrorCode` does not drive HTTP status; the Postgres driver code does.** The filter reads `exception.error.originalError.driverError.code` off a `DatabaseException`: `23505` → 409 `ALREADY_EXISTS` (log `info`, constraint name only — the race where two requests both pass `enforceUnique`), `23503` → 409 `REFERENCE_CONFLICT` (log `warn`, constraint + table). Every other `DatabaseException` (including `DatabaseErrorCode.NOT_FOUND`) is a server error. Neither 409 carries `details`.
- **Anything thrown inside a `ServiceBase`/`ComposerBase` transaction body is reclassified as a server error.** The `try/catch` blocks around `createEntity`, `manager.save` + `afterUpdateInTransaction`, and `remove` funnel every error — even a deliberate `NotFoundException`/`BadRequestException` — through `DatabaseError.fromTypeOrmError`, so it surfaces as a 500 `INTERNAL_ERROR` (logged at `error`), not its original status. This includes `ComposerBase.composeNestedEntity`/`composeManyNestedEntity`'s `manager.findOneOrFail` on a nested `id` that doesn't exist. A distinct HTTP status for a failure must be thrown outside those `try` blocks — or, for bad input, caught earlier by the validator.
- **Never throw `DatabaseException`/`DatabaseError` directly from domain code.** They exist purely as the output type of `DatabaseError.fromTypeOrmError`. Domain services/controllers should let TypeORM errors propagate naturally out of a `ServiceBase`-wrapped call; for validation/business-rule failures throw `AppHttpException` (with an `error_constants.ts` code) or a stock Nest `HttpException` (`BadRequestException`, `NotFoundException`, etc. — e.g. `menu-items/services/menu-item.service.ts` and `orders/services/order.service.ts` both do this for snapshot-payload validation), never construct a `DatabaseException` by hand.
- **`GlobalHttpExceptionFilter`'s response envelope is fixed and every branch must populate it consistently:** `{ statusCode, timestamp, path, requestId, message, code, details }` (`requestId` from `resolveRequestId(request)`, always equal to the `X-Request-Id` response header), always via `response.status(status).json(customResponse)`. `classify()` maps, in order: `ValidationException` → 400 `VALIDATION_ERROR`, `details: { validationErrors }`; logged `warn` with `source: 'business'` and `errors: exception.errorMap.collectLoggedErrors()` only when the tree contains a code marked logged in `VALIDATION_ERROR_CODE_LOGGED` (`src/common/validation/validation-error-codes.ts`); `DtoValidationException` → 400 `INVALID_REQUEST`, `details: { fields }` (flat dotted paths, indexes as segments), logged `warn` with `source: 'dto'`, `dto`, `constraints: [{ path, constraint }]`; `DatabaseException` → 409s above, else server error; `HttpException` (incl. `AppHttpException`) with status ≥ 500 → server error; other `HttpException` (incl. `AppHttpException`) → its own status and `message`/`code`/`details` from the response body, **not logged** (401/403/404 are recorded only by the pino-http access line), except `AppHttpException` with code `REFERENCE_NOT_FOUND`, logged `warn` with `id`/`ids`; anything else (plain `Error`, `UnitConversionError`, …) → server error. New exception types need an explicit branch in `classify()` or they become a 500.
- **Server errors are opaque.** Response: 500, `code: 'INTERNAL_ERROR'`, generic message, no `details`. The internal message, `DatabaseError.details`, `originalError`, SQL and Postgres `detail` never reach the body — `DatabaseError` keeps them for logging only. Log: `error`, `source: 'server'`, `err: { type, message, stack }` (built explicitly from the original TypeORM error when there is one — never log the raw `QueryFailedError`, its `parameters` are request values), `pgCode`, `pgDetail`.
- **Every filter log entry carries** `requestId`, `method`, `route` (Express route pattern, e.g. `/menu-item-categories/:id`, falling back to `request.path` — never the query string), `userId`, `tenantId` (from `RequestContextService`). Never log the request body.
- **Only the filter logs errors.** There is no application logger wrapper; services, builders, validators and `DatabaseError.fromTypeOrmError` only throw. Don't add `logger.error`/`warn` calls where an error starts — put the context on the exception and let `classify()` decide the level.

## Gotchas

2026-10-03 — `RequestContextService.getRequestId()` returns a fresh `development-<uuid>` per call outside production, so it never matches the request's `X-Request-Id` in dev/test — read the id via `resolveRequestId(req)` (or the CLS `requestId` key) when it must match the header.
