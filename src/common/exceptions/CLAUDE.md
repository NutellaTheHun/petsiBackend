## Overview

This directory is the app's single translation layer between low-level failures (TypeORM/Postgres errors, validation errors, ad-hoc `HttpException`s) and the JSON error envelope every HTTP client sees. It has two halves: a set of typed exception classes/handlers that domain code (mostly `ServiceBase` and `BuilderBase`) throws or produces, and one `@Catch()` filter that turns whatever gets thrown into a uniform response body.

- `app-http-exception.ts` — `AppHttpException extends HttpException`. Constructor takes `(message, status, code?, details?)` and packs them into the Nest response body as `{ message, code, details }`. This is the one exception type meant to be thrown directly by application code when it needs to pick its own HTTP status/code (e.g. `BuilderBase.setPropById`/`setPropsByIds`/`setPropByName` in `src/common/base/builder.base.ts` throw `AppHttpException(..., HttpStatus.BAD_REQUEST, ENTITY_NOT_FOUND, { id })` when a foreign-key id passed into a create/update DTO doesn't resolve to a real row).
- `error_constants.ts` — string constants (`ENTITY_NOT_FOUND`, `DTO_VALIDATION_FAIL`, `SOMETHING_WENT_WRONG`, `EXIST`, `DUPLICATE`, `INVALID`, `MISSING`) meant to populate `AppHttpException.code`. In practice only `ENTITY_NOT_FOUND` is currently consumed anywhere (`src/common/base/builder.base.ts`); the rest are declared but not yet wired to a call site.
- `database-error.ts` — `DatabaseError` (a plain `Error` subclass, not an `HttpException`) plus `DatabaseErrorCode` enum (`CONSTRAINT`, `NOT_FOUND`, `CONNECTION`, `UNKNOWN`). Its static `DatabaseError.fromTypeOrmError(error)` is the single place that inspects a raw error and classifies it (see Enforced Patterns). It always returns a `DatabaseException`, wrapping the classified `DatabaseError` inside.
- `database-exception.ts` — `DatabaseException extends Error`, carries the classified `DatabaseError` on `.error` and a generic `message` (`'Database error occured'` by default). This is what actually gets thrown up to controllers/the filter.
- `database-exception.handler.ts` — `DataBaseExceptionHandler` (`@Injectable()`), constructed with an `AppLogger`. Its `handle(err, servicePrefix, requestId, action)` method calls `DatabaseError.fromTypeOrmError(err)`, logs it via `AppLogger.logError(...)`, and returns the `DatabaseException` for the caller to `throw`. It does not throw itself — callers are responsible for `throw this.databaseExceptionHandler.handle(...)`.
- `global-http-exception-filter.ts` — `GlobalHttpExceptionFilter` (`@Catch()` on everything), registered once in `src/main.ts` via `app.useGlobalFilters(new GlobalHttpExceptionFilter())`. It's the only place in the app that decides final `statusCode`/`message`/`code`/`details` for the HTTP response.

Key relationships:
- `src/main.ts` wires `GlobalHttpExceptionFilter` globally in `bootstrap()`; no per-controller or per-module filter registration exists, so this is genuinely app-wide.
- `src/common/base/service.base.ts` (`ServiceBase`) owns a private `DataBaseExceptionHandler` instance (constructed inline in its constructor, not injected via DI) and is the sole real caller of `.handle(...)`, wrapping every `create`, `update`, `findAll`, `findOne`, `remove`, and `getQueryBuilder` DB call in `try { ... } catch (err) { throw this.databaseExceptionHandler.handle(err, this.servicePrefix, requestId, '<ACTION>'); }`. Since virtually every domain module has a service extending `ServiceBase`, this handler is exercised on essentially every write and most reads across the app, even though no domain module imports `DataBaseExceptionHandler`/`DatabaseException` directly.
- `src/common/base/builder.base.ts` (`BuilderBase`) imports `AppHttpException`/`ENTITY_NOT_FOUND` directly and throws them when a queued `setPropById`/`setPropsByIds`/`setPropByName` step can't resolve a related entity — this is how "menuItemId 123 doesn't exist" errors surface as 400s with `code: 'ENTITY_NOT_FOUND'`, distinct from the DB-error path.
- `src/common/base/composer.base.ts` (`ComposerBase`) calls `manager.findOneOrFail(...)` for the update branch of `composeNestedEntity`/`composeManyNestedEntity`. TypeORM's `EntityNotFoundError` thrown there propagates out through the enclosing `ServiceBase.create`/`update` transaction's `try/catch`, so it too ends up going through `DatabaseError.fromTypeOrmError` (matched by the `error.name === 'EntityNotFoundError'` branch) rather than as a clean 404.
- `src/common/validation/validation-exception.ts`/`validation-exception.handler.ts` are a sibling pattern (same shape: a plain-`Error` exception + a handler that logs and returns it), and `GlobalHttpExceptionFilter` special-cases `ValidationException` the same way it special-cases `DatabaseException`.
- `src/modules/orders/controllers/order.controller.spec.ts` has a test literally titled "updateOrderResponse surfaces missing entity via DatabaseException" asserting that updating a non-existent order id rejects with `DatabaseException` (not `NotFoundException`) — see Enforced Patterns for why.

## Enforced Patterns

- **DB error classification happens in exactly one place and only recognizes two Postgres codes.** `DatabaseError.fromTypeOrmError` (`database-error.ts`) only special-cases `error instanceof QueryFailedError` with `pgError.code === '23505'` (unique violation → `DatabaseErrorCode.CONSTRAINT`) and `pgError.code === '23503'` (foreign key violation → `DatabaseErrorCode.CONSTRAINT`). Every other `QueryFailedError` falls into `DatabaseErrorCode.UNKNOWN`. Separately, `error.name === 'EntityNotFoundError'` maps to `DatabaseErrorCode.NOT_FOUND`. Anything else (plain `Error`s, Nest `HttpException`s like `NotFoundException`/`BadRequestException` thrown inside a `ServiceBase` try block, connection errors, etc.) falls through to `DatabaseErrorCode.UNKNOWN` too — there is no explicit `DatabaseErrorCode.CONNECTION` producer despite the enum value existing. A new Postgres error code that needs distinct handling (e.g. `23502` not-null, `23514` check) must be added as a new branch in `fromTypeOrmError`.
- **`DatabaseErrorCode` does not currently drive HTTP status.** `GlobalHttpExceptionFilter` treats every `DatabaseException` identically: `status = HttpStatus.INTERNAL_SERVER_ERROR`, `code = 'DATABASE_ERROR'`, `details = { databaseError: exception.error }` (the real `DatabaseErrorCode`/table/constraint info is preserved inside `details.databaseError`, just not reflected in `statusCode`). A unique-constraint violation on create and a totally unexpected query failure both currently return **500**, not 409/400. Anyone adding differentiated status codes needs to add that branching in the filter (or make `DataBaseExceptionHandler.handle` throw distinct `HttpException` subclasses per `DatabaseErrorCode`).
- **This "everything DB-related becomes 500" behavior also swallows legitimate 404s thrown inside a `ServiceBase` transaction.** `ServiceBase.update` calls `this.findOne(id, ...)` inside a `try { } catch (err) { throw this.databaseExceptionHandler.handle(err, ...) }` block. `findOne` throws a plain `NotFoundException()` when the id doesn't resolve; that gets caught by `update`'s `catch`, re-classified by `fromTypeOrmError` (matching none of the special cases), and re-wrapped as a `DatabaseException` with `DatabaseErrorCode.UNKNOWN` — turning a 404 into a 500. Exercised directly by `order.controller.spec.ts`'s `'updateOrderResponse surfaces missing entity via DatabaseException'` test. The same trap applies to `ComposerBase.composeNestedEntity`/`composeManyNestedEntity`'s `manager.findOneOrFail`. **Any error thrown inside a `ServiceBase`/`ComposerBase` transaction body — even a deliberate `NotFoundException`/`BadRequestException` — gets unconditionally reclassified and surfaces as a 500 `DATABASE_ERROR`, not its original status.** A distinct HTTP status for a failure inside that transaction must be thrown outside the `try` blocks that funnel into `databaseExceptionHandler.handle`.
- **Never throw `DatabaseException`/`DatabaseError` directly from domain code.** They exist purely as the output type of `DatabaseError.fromTypeOrmError`/`DataBaseExceptionHandler.handle`. Domain services/controllers should let TypeORM errors propagate naturally out of a `ServiceBase`-wrapped call; for validation/business-rule failures throw `AppHttpException` (with an `error_constants.ts` code) or a stock Nest `HttpException` (`BadRequestException`, `NotFoundException`, etc. — e.g. `menu-items/services/menu-item.service.ts` and `orders/services/order.service.ts` both do this for snapshot-payload validation), never construct a `DatabaseException` by hand.
- **`GlobalHttpExceptionFilter`'s response envelope is fixed and every branch must populate it consistently:** `{ statusCode, timestamp, path, message, code, details }`, always via `response.status(status).json(customResponse)`. The filter special-cases, in order: `AppHttpException` (reads `getStatus()` + the `{message, code, details}` response body), `ValidationException` (forces 400, `code: 'VALIDATION_ERROR'`, `details: { validationErrors: exception.errors }`), `DatabaseException` (forces 500, `code: 'DATABASE_ERROR'`), then falls back to any other `HttpException` (reads `getStatus()`, and `message`/`code`/`details` off its response body if it's an object), and finally a bare-`Error` fallback (`message = exception.message || 'Internal server error'`, status stays 500, `code`/`details` stay `undefined`). New exception types must either extend `AppHttpException` or add an explicit `else if` branch here — otherwise they silently fall into the generic 500 branch with no `code`.
- **`DataBaseExceptionHandler` must be given a `servicePrefix`, `requestId`, and `action` string on every call** (`ServiceBase` passes its own `servicePrefix` plus `this.requestContextService.getRequestId()` and a literal action tag like `'CREATE'`/`'UPDATE'`/`'FIND_ALL'`/`'FIND_ONE'`/`'REMOVE'`/`'GET_BUILDER'`) — these are purely for `AppLogger.logError` correlation and are not optional in the type signature.
