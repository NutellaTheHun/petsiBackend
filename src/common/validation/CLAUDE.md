## Overview

`src/common/validation` is the runtime, business-rule layer of validation — distinct from the class-validator decorators on DTOs (which only check shape/type of a single incoming payload). Everything here operates on a `ValidatorIdentityBaseInterface`-shaped "identity" (an object with optional `id`/`createId`, resolved from a DTO) and often needs to consult the database (uniqueness, existence, cross-entity constraints), which class-validator decorators can't do cleanly. The five files in this directory are:

- **`validatator-helper.ts`** — `ValidatorHelper<TEntity, TDto, TIdentity>`, a stateless grab-bag of reusable business-rule checks (existence, uniqueness, numeric bounds, conditional/mutual-required fields, duplicate-detection, etc). This is the real "meat" of the directory; almost everything else exists to support it.
- **`validation-error.ts`** — `ValidationErrorMap`, the mutable error tree every check writes into, plus `ValidationErrorResponse`/`ValidationErrorPayload` (the client-facing shapes) and test helpers (`findValidationErrorResponseByPath`, `expectValidationErrorPayload`, `expectValidationErrorCode`, `expectValidationErrorSize`) used throughout `*.validator.spec.ts` suites.
- **`validation-error-codes.ts`** — the closed `ValidationErrorCode` union: `MISSING_PROPERTY | INVALID_PROPERTY_VALUE | ALREADY_EXISTS | DUPLICATE_ITEMS | ONLY_ONE | IMMUTABLE_FIELD`. Every error added anywhere must use one of these codes.
- **`validation-exception.ts`** — `ValidationException`, a plain `Error` subclass wrapping a `ValidationErrorResponse`.
- **`validation-exception.handler.ts`** — `ValidationExceptionHandler`, wraps a `ValidationErrorResponse` in a `ValidationException` and logs it via `AppLogger.logError`.

How it's wired into the base-class hierarchy (`src/common/base`): every domain validator extends `ValidatorBase<T, I>` (or `NestedValidatorBase<T, I>` for validators only ever invoked as children). `ValidatorBase`'s constructor instantiates a fresh `ValidatorHelper<...>()` and exposes it as `protected helper`, so every subclass calls checks as `this.helper.enforceXxx(...)`. `ValidatorBase.validateDto` first calls the subclass's `resolveIdentity(dto, id)` to turn a create/update DTO into `I`, then calls the abstract `validateIdentity(identity, id)` which subclasses implement by building a `new ValidationErrorMap(id)` and threading it through one or more `this.helper.enforceXxx(...)` calls (and/or nested `validateNestedIdentity` calls). `getValidateResponse` converts a non-empty map to a `ValidationErrorResponse` via `ValidationErrorMap.buildResponse()`; `ServiceBase.create`/`update` throw a `ValidationException` directly when that response is non-null, and `GlobalHttpExceptionFilter` (`src/common/exceptions/global-http-exception-filter.ts`) catches it and returns HTTP 400 with `code: 'VALIDATION_ERROR'` and `details.validationErrors` set to that response.

Grepping `src/modules` confirms real adoption: `enforceExists` (16 files), `enforceUnique` (17 files), `enforceNoDuplicateElements` (6 files), `enforcePositive` (9 files), `enforceValidSize` (4 files), `enforceConditionalRequired`/`enforceOnlyOne` (2 files each), `enforceMutualRequired`/`enforcePropertyState` (1 file each) — `enforceArrayNotEmpty`, `enforceNonNegative`, `enforceValueInList`, and `enforceNotInList` currently have zero call sites in `src/modules`.

**Key relationships:**
- `ValidatorBase`/`NestedValidatorBase` (`src/common/base/validator.base.ts`, `nested-validator.base.ts`) own the `ValidatorHelper` instance and the `validateIdentity`/`resolveIdentity` contract; this directory only supplies the checks and the error-tree data structure, never the orchestration.
- `ValidationErrorMap` is the single mutable object passed by reference through an entire validation pass — from the root `ValidatorBase.validateIdentity` down through every `ValidatorHelper.enforceXxx` call and every nested `validateNestedIdentity` call (`addChild`).
- `ServiceBase.create`/`update` and `GlobalHttpExceptionFilter` are the only consumers of `ValidationException`; `ValidationExceptionHandler`'s `.handle()` method has no call sites anywhere in `src/` — it is currently dead code, so `ValidationException`s thrown from `service.base.ts` are never routed through `AppLogger.logError`.
- The test helpers in `validation-error.ts` are the standard way `*.validator.spec.ts` files assert on nested error trees (see `src/modules/roles/validators/role.validator.spec.ts`, `src/modules/orders/validators/order-container-item.validator.spec.ts`).

## Enforced Patterns

`ValidatorHelper` standardizes these business-rule categories, each returning a fixed `ValidationErrorCode`:

- **Existence** — `enforceExists` checks a foreign id exists via `repo.findOne({ where: { id } })` against the **database**, not any in-memory candidate list, and emits `INVALID_PROPERTY_VALUE`. `enforcePropertyState` also hits the DB but additionally throws a raw `NotFoundException` if the referenced entity is missing entirely (distinct from adding a validation error) before comparing `entity[field] !== targetValue`.
- **Uniqueness** — `enforceUnique` queries `repo.find({ where: { [field]: val } })` against the DB and adds `ALREADY_EXISTS` if any matching row's `id` differs from the identity's own `id`/`createId`. This is an **exact-match, case-sensitive** database query (no normalization anywhere in this file or in call sites checked) — two names differing only in case both pass as "unique."
- **Value constraints** — `enforcePositive` (`> 0`), `enforceNonNegative` (`>= 0`), `enforceValueInList`/`enforceNotInList` (membership against an explicit array), and `enforceValidSize` (a size id must appear in a foreign entity's array-valued relation) — all emit `INVALID_PROPERTY_VALUE`. All of these **short-circuit to a no-op when the value is `null`/`undefined`**, so callers must gate optional-field checks themselves if "field is required" is also a rule (see `OrderMenuItemValidator` guarding `if (identity.quantity !== undefined)` before calling `enforcePositive`).
- **Conditional/mutual requirements** — `enforceConditionalRequired(identity, hinge, hingeValue, dependents, errMap)` requires all `dependents` be non-null/non-empty when `identity[hinge] === hingeValue` (emits `MISSING_PROPERTY` per missing dependent); used by `OrderValidator` to require `deliveryAddress`+`phoneNumber` when `fulfillmentType === 'delivery'`. `enforceMutualRequired(dto, mutuals, errMap)` requires a group of properties be all-present or all-absent (one `INVALID_PROPERTY_VALUE` listing every field in the group) — used in `recipe.valdiator.ts`. `enforceOnlyOne(identity, first, second, errMap)` requires exactly one of two properties populated (errors on both-populated and both-empty) — used in `InventoryAreaItemValidator`/`RecipeIngredientValidator` for "reference by nested-create OR by existing id, never both/neither."
- **Array integrity** — `enforceArrayNotEmpty` requires a non-empty array (`MISSING_PROPERTY`); `enforceNoDuplicateElements(items, keyExtractor, field, errMap)` builds a map from a caller-supplied key to colliding item ids and emits one `DUPLICATE_ITEMS` error per colliding key with `ids` set to all colliding item ids. **Gotcha:** if `keyExtractor` returns `id == null` (an item with neither a persisted `id` nor a `createId`), this throws a synchronous `Error('id is required')` rather than adding a validation error — a malformed nested DTO here crashes the request instead of producing a 400.

**Contract a domain validator must follow to use these helpers correctly:**
1. Instantiate nothing — `this.helper` is already provided by `ValidatorBase`'s constructor; just call `this.helper.enforceXxx(...)`.
2. Create exactly one `ValidationErrorMap` per `validateIdentity` call, `new ValidationErrorMap(id)`, and pass that same instance (by reference) into every helper call and every nested `validateNestedIdentity` call — helpers mutate it in place; they never return a new map.
3. `errorMap.addError(code, ids?, fields?)` throws synchronously if `fields` is passed as an empty array — never call `addError` with `fields: []`; omit `fields` entirely instead.
4. For nested identities, never call the child validator's `validateIdentity` directly — call `childValidator.validateNestedIdentity(fieldName, childIdentity, rootErrorMap)` (defined on `ValidatorBase`). It resolves the child's own id (throwing if neither `id` nor `createId` is set), runs the child's `validateIdentity`, and only calls `rootErrorMap.addChild(field, childErrors)` if the child's map is non-empty.
5. Checks are async when they hit the DB (`enforceExists`, `enforcePropertyState`, `enforceUnique`, `enforceValidSize`, `enforceNotInList`) and synchronous otherwise. There is no aggregate ordering or short-circuit: `validateIdentity` implementations run every applicable check regardless of whether an earlier one already failed, so a single field can accumulate multiple error codes in one response.
6. Every `@param errMsg` in the JSDoc comments across `validatator-helper.ts` is stale/aspirational documentation — no actual method accepts an `errMsg` parameter. The only per-error customization available is the fixed `ValidationErrorCode` plus optional `ids`/`fields` arrays.
7. `IMMUTABLE_FIELD` is a valid code but has no corresponding `ValidatorHelper` method — `DynamicPropertyConfigValidator` calls `errorMap.addError('IMMUTABLE_FIELD', ...)` directly. This is the sanctioned escape hatch: when a business rule doesn't fit an existing `enforceXxx`, add errors straight to the `ValidationErrorMap` with an existing code rather than inventing a new helper or a new code without updating `validation-error-codes.ts`.
