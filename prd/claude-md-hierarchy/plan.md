# Hierarchical CLAUDE.md + debrief loop

## Problem

One global CLAUDE.md (from `/init`) is the only persistent context the agent gets about the codebase. It's a flat snapshot from whenever it was last run — no per-module depth, no record of module-specific gotchas, and no mechanism to keep it current as work happens. Separately, the `/do-task` → `/debrief-task` → `/review-debrief` loop (capture friction → cluster patterns → propose fixes) exists on paper but was never wired up, partly because it wasn't clear how to debrief in a fresh context without either burning the same context that just did the implementation, or losing the ability to see what actually happened.

## Solution

Two things, connected:

1. **Local CLAUDE.md files per directory.** Each of the 14 `src/modules/<domain>/` directories, plus 4 shared-foundation directories (`src/common/base`, `src/common/exceptions`, `src/common/validation`, `src/infrastructure/database/typeorm`), gets its own `CLAUDE.md` with a fixed 3-section template: Overview, Enforced Patterns, Gotchas. Claude Code already loads these automatically and on-demand whenever it reads a file in that directory — no extra plumbing needed to make them "get used."

2. **A debrief loop that actually runs.** `do-task` records its own session id when it finishes. A background agent then runs `debrief-task` in a completely fresh context, reading the session's transcript off disk (not conversation memory) to reconstruct what happened. Debriefs accumulate; `review-debrief` clusters them and proposes edits to the right CLAUDE.md (local or global) — but only as recommendations. It never writes anything itself.

## Decisions

**Scope of local files** — one `CLAUDE.md` per `src/modules/<domain>/` (14) plus `src/common/base`, `src/common/exceptions`, `src/common/validation`, `src/infrastructure/database/typeorm` (4). 18 total.

**Template** (fixed, 3 sections):
```
---
module: <path>
last_reviewed: <date>
---

## Overview
<what this directory does, key entities/relationships>

## Enforced Patterns
<rules that must be followed here, and why>

## Gotchas
<date> — <what went wrong> — <the correction now in force>
```

**Who writes what, and when:**
- Overview + Enforced Patterns: written/regenerated by the `/init-local` skill (new), which explores the directory and derives them. Re-running it on an existing file re-derives both sections fresh and shows a diff for confirmation before overwriting.
- Gotchas: written *only* by explicitly applying a `review-debrief` recommendation. Never auto-written, never touched by `/init-local`.
- `do-task` never writes to any CLAUDE.md.
- `review-debrief` never writes to any CLAUDE.md either — it only prints numbered recommendations (pattern, root cause, exact proposed text, which file). Applying one is a separate, explicit instruction from the user afterward (no dedicated apply-command; just "apply finding 2").

**`/init-local` invocation** — one directory per run, arg required: `/init-local src/modules/orders`. No bulk/`--all` mode. Pilot directory: `src/modules/orders`.

**Debrief mechanism** — `do-task`'s last step writes `session: $CLAUDE_CODE_SESSION_ID` into the task file's frontmatter, then spawns a background Agent running `/debrief-task <prd-slug> <task>`. That agent starts with zero shared context, reads the task file to get the session id, locates the matching transcript JSONL under `~/.claude/projects/<project-hash>/<session-id>.jsonl`, and reconstructs friction/deviations from it rather than from conversation memory. This also needs `debrief-task` to record which directories/modules were touched (parsed from Edit/Write tool calls in the transcript) so `review-debrief` knows which local CLAUDE.md file(s) are candidates for a given finding.

**Content migration for the existing global CLAUDE.md** — split by whether content is cross-cutting or directory-specific:
- Stays global: Commands, directory layout, Testing (atomic-test pattern — applies uniformly to every module's specs), Auth and roles, Caching, DB config.
- Moves to `src/common/base/CLAUDE.md`: the full base-class hierarchy diagram and lifecycle-hook docs (currently "Base class system" section).
- Moves to `src/modules/revision-history/CLAUDE.md`: revision-history internals and pruning-cron details (currently part of "Change detection + revision history").
- Global keeps a one-line pointer to each in place of the migrated detail.

**No changes needed** to `grill-me`/`grilling`, `to-prd`, or `to-issues` — they already explore the codebase before writing, so they benefit from local CLAUDE.md auto-loading for free.

## Task breakdown

1. **Build `/init-local` + template, pilot on `src/modules/orders`.** New skill at `.claude/skills/init-local/SKILL.md`. Explores a given directory, derives Overview + Enforced Patterns, writes/updates the file per the re-run semantics above. Validate by running it on `src/modules/orders` and reviewing the output.

2. **Build `src/common/base/CLAUDE.md` and `src/modules/revision-history/CLAUDE.md`, migrate global content.** Use `/init-local` (from task 1) to generate the initial Overview/Enforced Patterns for both, then hand-merge in the migrated detail from the current global CLAUDE.md. Trim the global file down to pointers per the Decisions above.

3. **Update `debrief-task`**: add transcript-based reconstruction (read `$session` from the task file, locate and parse the matching `.jsonl`, instead of relying on conversation memory) and add a `modules touched` field to its frontmatter/template, derived from Edit/Write calls in the transcript.

4. **Update `do-task`**: record `session: $CLAUDE_CODE_SESSION_ID` in the task file frontmatter as part of its existing "resolve and report" step, then spawn a background Agent running `debrief-task` for the same task.

5. **Update `review-debrief`**: make it read whichever local CLAUDE.md file(s) a debrief's `modules touched` points to, present findings scoped to the right file (local or global), and drop the existing auto-apply behavior (step 5 in its current SKILL.md) entirely — it only prints recommendations now.

6. **Roll out `/init-local` to the remaining 16 directories.** Not time-boxed — run as convenient once tasks 1–5 are validated. Order of preference: the other 3 shared-foundation dirs next (`src/common/exceptions`, `src/common/validation`, `src/infrastructure/database/typeorm`), then the remaining 12 domain modules.

## Out of scope

- The earlier headless-loop idea for auto-running every task unattended — not being revisited here; the background-Agent approach for `debrief-task` specifically works because its tool needs are minimal (Read/Bash/Write) and low-risk, which is a narrower and different thing than looping all of `do-task` unattended.
- A dedicated apply-command for review-debrief findings.
- Sub-module-level CLAUDE.md files (e.g. `src/modules/orders/services/CLAUDE.md`) — only directory-level for now.
