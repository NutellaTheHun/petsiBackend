## Deviations from plan

- **`InventoryAreaCountService` needed hand-written location authorization**, not the generic base-class check. `CreateInventoryAreaCountDto` has no client-facing `locationId` (only `inventoryAreaId`), so the task's own guidance ("stamp them via `this.getTenantId()`/`dto.locationId`") didn't directly apply; `createEntity`/`updateEntity` instead look up the referenced `InventoryArea`, copy its `tenantId`/`locationId`, and call the inherited `assertLocationAuthorized` explicitly — which required the `LocationScopedServiceBase.create()` conditional-check change noted above.
- **`OrderService.revertToRevision` had a latent tenant/location scoping gap** the task file didn't call out: its internal `manager.findOne(Order, ...)` calls bypass `TenantScopedServiceBase`/`LocationScopedServiceBase` entirely. Fixed by prepending `await this.findOne(orderId)` before the revert transaction.
- **`OrderRecurrenceService.cloneTemplateToOccurence` and `OrderService.applyOrderSnapshotV1`** construct `Order`/`OrderMenuItem`/`OrderContainerItem`/`RecurringOrderSchedule` directly via `manager.create`, bypassing the service/composer stamping path entirely (one runs from the hourly cron with no request context, the other from a revision revert). Both needed `tenantId`/`locationId` copied by hand from the template/reverting order — not mentioned in the task file, discovered by reading `order-recurrence.service.ts` end-to-end.
- **Fixed regressions in modules task 12 doesn't own**, surfaced only once `Order`/`OrderMenuItem`/`OrderContainerItem` became `NOT NULL` on `tenantId`/`locationId`: `src/modules/reports/services/report-execution.service.spec.ts` (raw `orderRepo.save()`/`orderMenuItemRepo.save()` calls needed the new columns) and `src/modules/seed/seed.service.spec.ts` (request-context tenant/admin switch needed to happen *before* the newly-scoped `InventoryAreaCountService`/`InventoryAreaItemService`/`OrderService` `findAll()` calls, not after). Neither was in task 12's "What to build," but leaving them broken would have left `npm run test` red.

## Friction points

- **`synchronize: true` schema sync fails outright once a `NOT NULL` column is added onto a table with existing rows** (tag: `wrong-assumption`) — same root cause task 11's debrief already flagged, hit again here: `QueryFailedError: column "tenantId" of relation "inventory_area_items" contains null values`. `npm run clearTestDb` itself couldn't recover from this (it also calls `synchronize` before it can clear anything — chicken-and-egg). Worked around by running `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` directly via `psql` (11 times across the session, once per debugging cycle after adding a new NOT NULL column or discovering stale rows). This is now a recurring, predictable cost for every task in this PRD that adds a required column — worth the PRD/task-file explicitly naming the `DROP SCHEMA`/`psql` workaround rather than every task rediscovering it independently.
- **`/debrief-task` can't be dispatched from a background `Agent`** (tag: `missing-context`) — same gap task 11's debrief already flagged: `do-task`'s final step spawns a background `Agent` to invoke `/debrief-task`, but the skill has `disable-model-invocation: true` and refuses when triggered that way (`<task-notification>` result: `"failed: /debrief-task cannot run in this background job..."`). The debrief only actually ran once the user invoked it directly as a slash command in a later turn.
